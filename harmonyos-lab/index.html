第三步：最重要的思维转变 —— 命令式 vs 声明式
一句话区别：Web 里（用 DOM 时）你是"指挥官"——找到元素、改它、它再重绘，每一步都你操心；鸿蒙里你是"甩手掌柜"——只改数据，界面怎么变是框架的事。下面这个演示，亲手跑一遍两边的流程：
🐢 命令式（JS / DOM 思维）手动找到元素 → 手动改它
script.js（Web 写法）
// ① 先找到那个元素
const el = document.getElementById('greet');
// ② 手动改它的内容
el.textContent = '你好，鸿蒙';
// ③ 浏览器重绘 → 你看到变化
// （每一步都得你亲自操心）
1getElementById 先"抓到"那个元素 —— 抓错了就白干
2手动把 textContent 改成新文字
3浏览器重绘，你才看到变化
🚀 声明式（鸿蒙思维）只改数据，剩下交给框架
Index.ets（鸿蒙写法）
@State message: string = 'Hello World';

// 你只说一句话：把数据改成新值
this.message = '你好，鸿蒙';

// 然后什么都不用管 ——
// 框架自动找到所有用到 message 的地方并刷新
1改变量 this.message = '…'（唯一你要做的）
2框架发现「@State 标记的数据变了」
3自动刷新所有用到它的地方（你一行都不用多写）
屏幕上显示的效果： Hello World

用途Web 习惯鸿蒙推荐说明

⚠️第五步：带着前端思维最容易踩的 8 个坑
每一条都是"在 Web 里理所当然、在鸿蒙里直接报错"的写法。现在看一遍，能省你几天调试时间。
❌ 坑 1：逛去找 DOM 节点
"没有 document！"鸿蒙没有 DOM 概念。
👉 正确姿势：用状态变量描述界面，改数据而不是改节点。
document.getElementById 在鸿蒙里不存在。
❌ 坑 2：想在 build() 里写逻辑
build() 只是"界面图纸"，不能 console.log、不能赋值、不能写复杂计算。
👉 逻辑写到普通方法里（onClick 回调、生命周期函数），build 里只放 UI 描述。
❌ 坑 3：找不到 CSS 文件
鸿蒙工程里没有 .css。样式通过链式属性跟在组件后面：.width(100).backgroundColor('#fff')。
👉 习惯"属性即样式"。
❌ 坑 4：习惯性地写 px
.fontSize(16) = 16vp（推荐）；写 '16px' 也能跑，但不同屏幕会不一样。
👉 布局用 vp（直接写数字），字体用 fp。
❌ 坑 5：用 == 比较数组
和 JS 一样，两个内容相同的数组 [1,2]==[1,2] 是 false。
👉 用 a.join(',') === b.join(',') 或逐项比较（项目 4 的密码验证就是这么做的）。
❌ 坑 6：存完数据忘记 flush
Preferences 的 put() 只写内存，必须 await flush() 才落盘，否则 App 一关数据就没了。
👉 口诀：put 之后必 flush。
❌ 坑 7：组件名小写开头
struct myCard 不能被当组件使用，必须 MyCard。
👉 组件、类型一律大驼峰；变量、函数小驼峰——和你在 JS 里的命名习惯一致。
❌ 坑 8：先 runJavaScript 再等加载
Web 组件里，网页没加载完就执行 JS 会静默失败。
👉 等 onPageEnd 回调里再调用（项目 5 演示里有日志可以观察时机）。

①鸿蒙操作系统是个啥？
💬 说人话
安卓管手机、Windows 管电脑、watchOS 管手表——各管各的。而鸿蒙的野心是：手机、电视、手表、车机、音箱……用同一套系统全部打通。你在手机上没看完的视频，上了车可以接着看，这就是"全场景"和"分布式"。

HarmonyOS 是华为开发的面向全场景的分布式操作系统。对开发者来说，只需要记住三件事：

  • 一次开发，多端部署：写一套代码，自动适配手机 / 平板 / 手表等不同屏幕。
  • 分布式能力：不同设备之间可以互相调用硬件（比如手机调用电视的摄像头）——这是鸿蒙的看家本领。
  • 面向未来的生态：鸿蒙 NEXT 起，系统已经完全自研底座，学习鸿蒙开发正是好时候。
🧠
考试/面试常问：鸿蒙的三大特征 = 全场景 + 分布式 + 一次开发多端部署。记这三个词就够了。

为什么要有"应用模型"？FA 和 Stage 是什么关系？
鸿蒙早期用的是 FA 模型（Feature Ability），从 API 9 开始官方推荐 Stage 模型，新项目一律用 Stage。

为什么换？FA 模型里"能力"和"窗口"缠在一起，多设备、多窗口场景下很别扭。Stage 模型把两者分开：UIAbility 管能力，WindowStage 管窗口，结构更清晰——这就是"舞台（Stage）"名字的由来。

考试/教材里讲的一切默认都是 Stage 模型，其余内容了解即可。

②装饰器五兄弟：@Entry / @Component / @Builder
"装饰器"就是写在代码上方的 @开头标签，给代码附加特殊含义。
装饰器用在哪作用（一句话）
@Entrystruct这个页面是"路由能的入口页"，一个页面只有一个
@Componentstruct这是可复用的自定义组件（积木）

@Link变量和父组件"共享"数据（双向，改哪边都同步）

那 @ 装饰器是什么？你在 JS 里用过 async 这种"写在函数前面的关键字"吧？鸿蒙的 @State 是同一类东西——给下面那行代码贴个标签，让编译器赋予它特殊含义。

再类比 React：useState 是"函数调用式"的声明状态，鸿蒙的 @State 是"标签式"的声明状态。目的完全一样：声明一份会自动触发界面刷新的数据。所以你已经有"状态驱动界面"的思维了，只是换个记号。

③状态管理：数据一变，界面就变（本章核心）
💬 说人话
传统写界面：数据改了，你得自己去"找到那个文字框、手动改文字"。
鸿蒙写界面：你只管改数据，系统自动帮你刷新所有用到该数据的地方。中间这个"自动"的魔法，就是装饰器在起作用。

@State 记忆法

「自己的小金库」——组件私有，自家人用，变了自家界面刷新。

@Prop 记忆法

「复印件」——父组件给你一份拷贝，你改你的，原件不受影响（单向：父→子）。

@Link 记忆法

「共用一张银行卡」——父子共享同一份数据，谁改都同步（双向绑定）。

// 父组件：数据源头
@Entry
@Component
struct ParentPage {
  @State count: number = 10;          // 父组件自己的状态

  build() {
    Column() {
      Text('父组件: ' + this.count)
      ChildCard({ count: this.count })              // @Prop 用法：传值进去
      ChildPanel({ countLink: $count })             // @Link 用法：加 $ 传引用
    }
  }
}

// 子组件 A：@Prop —— 只收不还（单向）
@Component
struct ChildCard {
  @Prop count: number;                // 从父组件拷贝一份
  build() { Text('子组件收到: ' + this.count) }
}

// 子组件 B：@Link —— 双向绑定
@Component
struct ChildPanel {
  @Link countLink: number;            // 和父组件同一份数据
  build() {
    Button('子组件 +1')
      .onClick(() => {
        this.countLink++;             // 改这里，父组件的 count 也同步变
      })
  }
}
🎯
考点提醒：@Prop 是单向（父改子变，子改父不变）；@Link 是双向（父子互相同步），用 $变量名 的方式传递。子组件不能直接修改 @Prop 的值，这是常考判断题。

Preferences 基本用法
import { preferences } from '@kit.ArkData';

// ① 获取实例（拿柜子）：第一个参数是上下文，第二个是柜子名
let store = await preferences.getPreferences(context, 'MyStore');

// ② 存数据：柜子里放一个键值对
await store.put('pattern', '0,1,2,4,6,7,8');   // key 是 'pattern'，value 是图案字符串
await store.flush();      // ⚠️ 关键一步：flush 才真正写入磁盘！

// ③ 读数据：从柜子里取
let value = await store.get('pattern', 'default');   // 第二个参数是"取不到时的默认值"

// ④ 删数据
await store.delete('pattern');
await store.flush();

你会用 localStorage 的话，Preferences 就是"异步版的 localStorage"，用法直接对照：

▸ 鸿蒙：Preferences（异步、要 flush）
store.ets

④PatternLock：九宫格组件（本项目的主角）
💬 说人话
官方已经把"九宫格画图案"这个组件做好了，你只管两件事：调样式（点多大、线多粗、什么颜色）和 接回调（用户画完了，把画的是哪几个点告诉你）。回调给你的是一串数字，比如 [0, 1, 2, 4, 6]，分别对应九宫格上从左到右、从上到下的编号。
PatternLock 核心用法
@Entry
@Component
struct LockPage {
  @State message: string = '请绘制解锁图案';
  private savedPattern: string = '';         // 已保存的图案（实际项目存 Preferences）
  private controller: PatternLockController = new PatternLockController();

  build() {
    Column() {
      Text(this.message).fontSize(16)

      PatternLock(this.controller)             // 传入控制器，用于重置状态
        .sideLength(240)                       // 九宫格边长
        .circleRadius(10)                      // 圆点半径
        .pathStrokeWidth(14)                   // 连线粗细
        .regularColor('#C9D4E6')               // 未选中点的颜色
        .selectedColor('#0A59F7')              // 选中点的颜色
        .activeColor('#66A3FF')                // 高亮点颜色
        .pathColor('#0A59F7')                  // 连线颜色
        .onPatternComplete((input: number[]) => {   // 画完的回调
          const str = input.join(',');         // 例：'0,1,2,4'
          if (str === this.savedPattern) {
            this.message = '✅ 解锁成功';
          } else {
            this.message = '❌ 图案错误，请重试';
            this.controller.setChallengeResult(PatternLockChallengeResult.WRONG);
            this.controller.reset();           // 重置九宫格
          }
        })
    }
  }
}
input 参数

①ArkWeb：给 App 开一扇"网页窗口"

③双向通信：App 与网页的"打电话"机制
📞 方向一：App → 网页
用 controller.runJavaScript('函数名()')
相当于 App 拿起电话打给网页："执行一下你那边叫 changeColor 的函数！"
时机要求：必须等网页加载完（onPageEnd 后）
📞 方向二：网页 → App
用 javaScriptProxy 把 App 的对象"注册"进网页的 window
网页里就能直接 window.对象名.方法() 调用 App 的能力
时机要求：推荐在 onControllerAttached 时注册
两个方向的完整代码
import { webview } from '@kit.ArkWeb';

// —— 应用侧：准备一个"可以被网页调用"的对象 ——
class ShopBridge {
  showToast(msg: string) {
    console.info('网页调用了我：' + msg);   // 收到网页的"电话"
  }
  getToken(): string {
    return 'APP_TOKEN_9527';               // 网页需要的数据，App 给它
  }
}

@Entry
@Component
struct ShopPage {
  controller: webview.WebviewController = new webview.WebviewController();
  bridge: ShopBridge = new ShopBridge();

  build() {
    Column() {
      // ① App → 网页：加载完成后执行网页里的 JS 函数
      Button('给网页换个背景色')
        .onClick(() => {
          this.controller.runJavaScript("setBgColor('#EAF2FF')");
        })

      Web({ src: $rawfile('shop.html'), controller: this.controller })
        .javaScriptAccess(true)                    // 允许执行 JS
        // ② 网页 → App：把 bridge 注册进网页
        .javaScriptProxy({
          object: this.bridge,                     // 要注入的对象
          name: 'shopBridge',                      // 网页里通过 window.shopBridge 使用
          methodList: ['showToast', 'getToken'],   // 允许被调用的方法清单
          controller: this.controller
        })
        .onPageEnd(() => {
          console.info('网页加载完成，现在可以放心 runJavaScript 了');
        })
    }
  }
}
⚠️
两个高频坑：① 网页没加载完就 runJavaScript → 函数不存在，静默失败；② methodList 里写错方法名 → 网页调用时报"方法不存在"。调试时记得给 Web 开启调试开关，用浏览器那套开发者工具排查。

💬 说人话

②HTTP 与 RCP：两种"点外卖"的方式

HTTP 请求三段式（发送 → 等待 → 处理）
import { http } from '@kit.NetworkKit';
import { BusinessError } from '@kit.BasicServicesKit';

let httpRequest = http.createHttp();          // ① 创建请求对象

httpRequest.request(
  'http://localhost:3000/api/news',           // 请求地址
  {
    method: http.RequestMethod.GET,           // 请求方法
    header: { 'Content-Type': 'application/json' }
  },
  (err: BusinessError, data: http.HttpResponse) => {
    if (!err) {
      // ② 成功：data.result 是服务器返回的"数据包"（记得解析 JSON）
      let list = JSON.parse(data.result as string);
      console.info('拿到 ' + list.length + ' 条数据');
    } else {
      // ③ 失败：断网 / 服务器没开 / 超时，都要处理！
      console.error('请求失败: ' + JSON.stringify(err));
    }
  }
);
⚠️
权限别忘加：使用网络功能前，在 module.json5 里声明 "ohos.permission.INTERNET"，否则请求会直接失败——这是新手最常见的翻车点。

④PanGesture：把手势变成功能
滑动快进的核心代码
.gesture(
  PanGesture({ direction: PanDirection.Horizontal })   // 只关心水平滑动
    .onActionStart(() => {
      this.startTime = this.currentTime;     // 记住开始滑动时的进度
    })
    .onActionUpdate((event: GestureEvent) => {
      // offsetX 是相对起点的滑动距离，按屏幕宽度折算成秒数
      const delta = event.offsetX / this.screenWidth * 60;   // 全屏滑完 = 60 秒
      this.targetTime = this.startTime + delta;
      this.showHint = '快进到 ' + format(this.targetTime);   // 显示提示浮层
    })
    .onActionEnd(() => {
      this.avPlayer.seek(this.targetTime * 1000);            // 松手才真正跳转
      this.showHint = '';
    })
)
💡
核心思路：滑动时只更新"提示"，松手时才真正 seek。这样既跟手、又不会疯狂触发跳转。

①元服务 vs 传统应用：到底差在哪？
💬 说人话
传统 App 像"搬进家里的大件家具":要下载（搬家）、要安装（组装）、占地方（存储）。
元服务像"便利店"：不用安装，到店就用，用完就走；需要时以卡片的形式出现在桌面、负一屏、甚至扫码/搜索的结果里。
📦 传统应用（App）
  • 需要下载安装包、占用存储空间
  • 需要注册/登录（通常）
  • 桌面图标进入，层级深
  • 适合功能复杂、高频使用的场景
  • 以"安装量"为目标
✨ 元服务（Atomic Service）
  • 免安装，即点即用，用完即走
  • 账号可"一键登录"，降低门槛
  • 卡片直达：桌面卡片 / 扫码 / 搜索 / 小艺建议
  • 适合轻量、低频、即时的场景（充电、点餐、查快递）
  • 以"服务直达率"为目标
💡
同一个 App 不能"又是应用又是元服务"——它们是两种独立形态，但可以共享一套代码库和卡片资源。考试常考这个区别。

③工程结构与状态变量：代码怎么组织
状态变量设计（组件的"记忆"）
@Entry
@Component
struct ChargingPage {
  @State batteryLevel: number = 42;        // 电量（0~100）
  @State isCharging: boolean = false;      // 是否正在充电
  @State chargeMode: string = '标准';      // 模式：快充/标准/定时
  @State power: number = 0;                // 当前功率 kW
  @State elapsed: number = 0;              // 已充时长（秒）
  @State statusText: string = '未充电';    // 状态文案

  // 定时器：充电时每秒更新一次
  private timerId: number = -1;

  startCharging() {
    this.isCharging = true;
    this.statusText = '充电中';
    this.timerId = setInterval(() => {
      this.batteryLevel = Math.min(100, this.batteryLevel + 1);   // 电量 +1
      this.elapsed += 1;
      this.power = this.chargeMode === '快充' ? 7.2 : 3.6;         // 功率跟着模式变
      if (this.batteryLevel >= 100) {
        this.stopCharging();
        this.statusText = '充电完成';
      }
    }, 1000);
  }

  stopCharging() {
    this.isCharging = false;
    this.power = 0;
    if (this.timerId !== -1) { clearInterval(this.timerId); this.timerId = -1; }
  }
}
状态变量四原则
① 能被 UI 用到的数据才用 @State；
② 数据变化 → 界面自动刷新，不要手动改 UI；
③ 定时器、控制器这类"工具对象"用普通变量存；
④ 组件销毁时记得清理定时器（onDestroy 里 clearInterval）。
业务逻辑分离
电量计算、功率换算这类逻辑，建议抽成单独的函数/工具类（比如 ChargingCalculator），组件里只管"调用 + 更新状态"。逻辑和界面分开，代码才好维护——这就是"工程结构"的意义。
⇄ 前端对照 · "迁移完成"自检清单

做完这个综合项目，对着下面清单自查——能全部打勾，说明你已经完成从 Web 到鸿蒙的思维迁移：

  • 我不再寻找 DOM 节点，而是声明 @State 变量来跟踪状态
  • 我不再写 CSS 文件 / 类名，而是用链式属性描述样式
  • 我不再拼 HTML 字符串，而是用 ForEach / 组件嵌套渲染列表
  • 我不再手动"更新界面"，只改数据（框架自动刷新）
  • 我的尺寸单位是 vp / fp，不再是 px
  • 我知道：存数据要 flush、请求要 权限、跳转要 登记路由

❓新手 FAQ
Q1：要先把 TypeScript 学完再学鸿蒙吗？
不用。本课程路线就是"直接学 ArkTS"，语法边用边学。有任意一门语言基础（Python/C/Java 都行）会更轻松，零基础也能跟。
Q2：没有华为手机能学吗？
能。DevEco Studio 自带模拟器，足以完成本课程所有练习。后期想调试真机再考虑华为设备。
Q3：电脑什么配置够用？
内存 16GB 起步（8GB 会很卡），预留 20GB 以上磁盘装 SDK 和模拟器。
Q4：模拟器起不来怎么办？
常见原因：① 没开启电脑的虚拟化（BIOS 里开 VT-x/AMD-V）；② 磁盘空间不足；③ 杀毒软件拦截。按顺序排查。
Q5：代码报错看不懂怎么办？
三步走：① 把 错误码/关键句复制去官网文档搜索；② 论坛搜索同样错误；③ 还不行就去 GitHub 的 issues 或论坛发帖（附上完整报错和代码片段）。
Q6：学完这 10 个项目能做什么？
能独立开发常规的鸿蒙应用/元服务：界面、数据、网络、媒体、卡片全流程都覆盖了。接下来可以挑战官方示例仓库里的完整项目。
📚完整术语速查（全课程版）
ArkTS

鸿蒙应用开发语言，基于 TypeScript 强化静态检查，语法兼容 TS 生态。

ArkUI

声明式 UI 框架："描述界面 + 状态驱动"，数据变了自动刷新 UI。

Stage 模型

推荐的应用程序模型：UIAbility 管能力、WindowStage 管窗口、Page 管界面。

UIAbility

应用的基本功能单元，拥有完整生命周期（onCreate → … → onDestroy）。

HAP

HarmonyOS Ability Package，应用模块的安装包，一个应用可含多个 HAP。

@Entry

页面入口装饰器，标记路由能跳转到的"页面级"组件。

@Component

自定义组件装饰器，让一段 struct 变成可复用的 UI 积木。

@State / @Prop / @Link

状态管理三兄弟：自己的状态 / 单向拷贝 / 双向共享。

@Builder

把一小段 UI 封装成可复用的"UI 工厂函数"。

ForEach

列表渲染：把数组的每一项变成界面上的一个组件。

router

页面路由：pushUrl 跳页、back 返回、携带 params 传参。

ArkData

数据管理家族：Preferences（键值）、分布式键值数据库、关系型数据库 RDB。

Preferences

轻量键值存储：put / get / delete + flush（别忘了写盘）。

PatternLock

九宫格手势组件，onPatternComplete 回调返回经过的点编号数组。

ArkWeb / Web 组件

在应用内嵌网页；runJavaScript 应用调网页，javaScriptProxy 网页调应用。

Form Kit

服务卡片框架：桌面小窗口，onAddForm / onUpdateForm / onRemoveForm 生命周期。

Network Kit

网络服务：HTTP 请求（@ohos.net.http）、RCP、网络状态监听。记得声明 INTERNET 权限。

Media Kit / AVPlayer

音视频播放：idle → initialized → prepared → playing ⇄ paused → … 状态机管理。

XComponent

提供 Surface 的"画布组件"，视频画面等自绘内容渲染在它上面。

PanGesture

拖动/滑动手势：左右滑调进度、上下滑调音量，是播放器手势的基础。

元服务

免安装、即用即走的轻量应用形态，通过卡片直达服务。

DevEco Studio

官方一站式 IDE：开发、预览、模拟器、调试、上架。
